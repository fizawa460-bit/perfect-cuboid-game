# Stage14-num1 — B=2m baseline cross-check and profiler

> STATUS: `STAGE14_NUM1=COMPLETE_BASELINE_CROSSCHECK_AND_PROFILE`
>
> CLASSIFICATION: exact finite census / engineering baseline only.
>
> NO asymptotic, square-root-law, or perfect-cuboid existence/nonexistence claim is made here.

## 1. Purpose

Stage14-num1 establishes the immutable numerical kernel that every later `14-num` optimization must reproduce before larger cutoffs are trusted.

The frozen population is

\[
0<a<b<c,\qquad \gcd(a,b,c)=1,
\]

\[
a^2+b^2+c^2=d^2,\qquad d\le 2,000,000,
\]

with at least two integral face diagonals.

## 2. Exact enumerator inventory

The repository currently contains two genuinely different Stage14-2 construction families.

1. `stages/stage14/scripts/14-2/two_face_census.py`
   - choose a Pythagorean face `x^2+y^2=p^2`;
   - extend the face diagonal by `p^2+z^2=d^2`;
   - canonicalize and recompute all face-square flags.

2. `stages/stage14/scripts/14-2/shared_leg_crosscheck.py`
   - first pair two Pythagorean faces on a common leg;
   - only afterwards test the integer space diagonal;
   - canonicalize and recompute all face-square flags.

The later graph kernel `stages/stage14/scripts/14-4/rank_jump_graph_audit.py` uses the first hypotenuse/leg-index family but retains only two-plus-face objects and then builds the active-face graph. Downstream `s`-track audits import this graph kernel. The `t1` baseline consumes the frozen two-route Stage14-2 census rather than introducing a third enumeration family.

Num1 locally reimplements the two independent construction families in one audit script so equality is checked at the **object-set** level rather than only at the count level.

## 3. Full B=2m object-set equality

The two generated sets agree exactly.

```text
route A = hypotenuse -> space-diagonal gluing
route B = shared-leg face pairing -> space-square test
route A object set == route B object set = true
```

\]

\[

\]

The raw-pair graph also reproduces the existing Stage14 locks:


Direction labels are not imported from an old report. They are recomputed from the exact three-bit face mask:

```text

```

Primitiveness, `0<a<b<c`, space-square identity and all three face-square flags are independently rechecked on every retained object.

## 4. Canonical ledger hashes

Canonical cuboid identity is `(a,b,c,d)`. The main baseline ledger digest additionally includes the face mask.

Encoding:

```text
sort lexicographically
write one ASCII line per object:
a,b,c,d,mask\n
SHA-256 the resulting byte stream
```

## 5. Deterministic workload profile

At `B=2,000,000` the common Pythagorean index contains

```text
integer Pythagorean triples  = 4,181,998
hypotenuse index keys        = 1,458,419
hypotenuse index entries     = 4,181,998
leg index keys               = 1,225,696
leg index entries            = 8,363,996
```

### Route A — hypotenuse / space-diagonal gluing

```text
candidate glues                           = 28,754,577
rejected nonprimitive                     = 23,286,679
face-mask tests after primitive filter    =  5,467,898
rejected with <2 integral faces           =  5,467,186
duplicate two-plus records suppressed     =        356
distinct retained two-plus objects        =        356
```

Thus almost every primitive glued record is still a one-face object; only the tiny two-face tail reaches the num ledger.

### Route B — shared-leg audit

```text
candidate shared-leg face pairs           = 147,280,537
rejected nonprimitive                     = 112,537,069
rejected because space diagonal nonsquare =  34,743,105
space-square hits above cutoff            =           7
duplicate retained records suppressed     =           0
distinct retained two-plus objects        =         356
```

The second route is intentionally an audit route, not a proposed production enumerator. Its dominant nested shared-leg pair scan examines about `147.3m` pairs, more than five times the candidate volume of Route A.

## 6. Reference resource profile


These values are environment-specific engineering observations and are **not** exact regression locks. Num2 must primarily preserve the deterministic object hashes and workload semantics; runtime/RSS comparisons must be made on comparable runners.

## 7. Bottleneck decision for num2

There are two different bottlenecks depending on role.

- Audit route: the `147,280,537` shared-leg pair scan dominates and should remain an independent correctness oracle rather than the default large-B production path.
- Production-family route: the large Pythagorean indexes plus `28,754,577` glue candidates are the immediate engineering target. After the primitive filter, `5,467,898` exact face-mask tests produce only `356` retained objects.

Therefore num2 should first investigate indexed/incremental production without weakening the independent shared-leg oracle. No optimization may be accepted unless all four frozen SHA-256 digests above remain unchanged at `B=2m`.

## 8. Perfect-cuboid handling
